# ADR-0005: Источник событий — TicketPro через JSON-LD

**Статус:** Accepted
**Дата:** 2026-11-04

## Контекст
Открытые сессии должны поддерживать события: концерт, спектакль, выставка,
спортивное шоу. Нужны события в Минске и Беларуси. Внешние event-API
(Ticketmaster, Eventbrite, KudaGo) либо плохо покрывают Минск, либо недоступны,
либо требуют ключей/аккаунтов. Пользователь предложил брать данные из TicketPro
и отрисовывать карточки самим.

Проверка показала:
- страницы событий TicketPro отдают schema.org JSON-LD `Event`;
- страницы площадок отдают schema.org `Place` с `geo` (lat/lon);
- `robots.txt` запрещает только кабинеты/корзину/чекаут, не страницы событий.

## Варианты
### A. Официальный международный API (Ticketmaster/Eventbrite)
- Плюс: стабильный контракт, лимиты, документация.
- Минус: слабое/непредсказуемое покрытие Минска; ключи и условия.

### B. TicketPro через публичные JSON-LD (выбран)
- Плюс: покрытие Минска, готовые поля, координаты площадок, не нужен ключ.
- Минус: не официальный API; вёрстка/JSON-LD могут измениться; вопросы условий.

### C. Ручные карточки событий
- Плюс: надёжно, без внешних зависимостей.
- Минус: пользователь вводит всё вручную; нет каталога.

### D. Скрапинг вёрстки TicketPro
- Плюс: можно достать больше полей.
- Минус: хрупко, сложнее поддерживать, выше риск нарушить условия.

## Решение
Вариант B + C как fallback:
1. **Основной источник — TicketPro JSON-LD**.
2. **Fallback — ручная карточка события**.
3. **Ticketmaster** — второй провайдер на будущее (абстракция `EventSource`).

Архитектура:
- `proxy` (Fastify) — единственное место, где ходят запросы к TicketPro.
- `GET /events/search?limit=&category=` — берёт список ссылок со страницы
  TicketPro, парсит JSON-LD событий, затем JSON-LD площадок для координат.
- `POST /events/import` с `{url}` — импорт одного события по ссылке.
- Кэш 15 минут, задержка между запросами, User-Agent, таймауты.
- Нормализация в `EventItem`: id, title, description, startsAt, endsAt,
  venueName, address, city, country, lat, lon, imageUrl, url, price, source.
- Приложение рисует свои карточки; данные — с атрибуцией «Данные: TicketPro»
  и ссылкой на событие.
- В комнате хранится снимок события, чтобы сессия была воспроизводима.

## Правовые и этические ограничения
- Это публичные структурированные данные, а не официальный API.
- Уважать `robots.txt`, не обходить защиту, не долбить сайт.
- Кэшировать, ограничивать частоту, указывать источник.
- Для production нужно соглашение с TicketPro или официальный фид.
- В тексте диплома зафиксировать: прототип, ограничения, риски.

## Последствия
- R2 становится больше на ~1.5–2 недели.
- Появляется зависимость от внешнего сайта; нужен fallback и тесты.
- Появляется сильный кейс для теории: JSON-LD, web scraping ethics,
  нормализация, кэширование, устойчивость к изменениям.
- Ticketmaster можно добавить позже без переделки UI.

## Проверка (2026-11-04)
- `POST /events/import` с реальной ссылкой TicketPro вернул событие:
  `Zoloto`, `2026-11-08T19:00:00`, «Дворец спорта», `53.912589, 27.548675`,
  цена `145 BYN`.
- `GET /events/search?limit=2` вернул 2 события с координатами площадок.
- Оба запроса уложились в ~0.4 с и ~1.1 с локально.
