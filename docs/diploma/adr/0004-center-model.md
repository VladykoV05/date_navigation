# ADR-0004: Модель центра встречи для N участников

**Статус:** Proposed
**Дата:** 2026-11-04

## Контекст
Сейчас «равноудалённая точка» — это точка на маршруте между двумя участниками,
выбранная по половине времени в пути (`osrm_remote_data_source.dart:65`,
`_findPointByHalfDuration`). Для приватной комнаты это работает, но:
- зависит от профиля маршрута (сейчас driving);
- не обобщается на 3+ участников;
- не учитывает, что места ищутся вокруг центра, а не на линии между точками.

Открытые сессии требуют модели, которая даёт разумный центр для N точек и
объяснима на защите.

## Варианты
### A. Геометрический центроид/медиана
- Плюс: просто, быстро, без внешних API.
- Минус: не учитывает дороги, время в пути, барьеры (реки, пробки).

### B. Середина маршрута (текущая)
- Плюс: уже есть, учитывает дороги для 2.
- Минус: только 2 участника, зависит от порядка точек, не изохрона.

### C. Минимизация суммарного времени в пути (1-медиана/Weber)
- Идея: кандидаты — точки участников + топ-N мест; матрица времён OSRM
  `/table`; выбрать кандидата, минимизирующего сумму времён (эффективность)
  или максимум (справедливость).
- Плюс: учитывает дороги, обобщается на N, объяснимо.
- Минус: больше запросов, зависит от `/table`, нужен кэш и fallback.

### D. Пересечение изохрон
- Идея: построить изохроны «15/30 минут» от каждой точки, взять пересечение.
- Плюс: наглядно, честно по времени.
- Минус: сложнее реализовать, demo OSRM не даёт готовых изохрон; нужна
  аппроксимация.

## Решение
Гибрид:
1. **Приватная комната (2 участника):** оставить текущую середину маршрута как
   быстрый путь; она объяснима и уже протестирована.
2. **Открытая сессия (N):** кандидаты = точки участников + топ-N мест вокруг
   геометрического центроида; матрица времён через OSRM `/table`; выбор
   кандидата по критерию **min(max duration)** (справедливость), tie-breaker —
   min(sum duration) (эффективность).
3. **Fallback:** если `/table` недоступен — геометрическая медиана (Weber)
   по haversine; если и это невозможно — центроид.
4. В комнате хранить `center`, `centerMethod`, `centerVersion`, чтобы результат
   был воспроизводим и объясним.

Почему не D: изохроны красивы, но для MVP и demo OSRM требуют аппроксимации;
их можно добавить как stretch после R5.

## Последствия
- R2 получает больше запросов к OSRM; нужен кэш и лимит кандидатов.
- Появляется объяснимая метрика справедливости (max duration).
- Приватный сценарий не ломается.
- Нужны тесты на 2/3/5 точек и на fallback.

## Проверка
- Сравнить A/B/C на 3–5 точках: max/avg duration, latency, число запросов.
- Тест: при недоступном `/table` возвращается медиана, UI не падает.
- Ручной smoke: 3 участника в открытой сессии, центр не «уезжает» к одному.
- Метрика: max duration и разброс времён; латентность построения центра.

## Открытые вопросы
- Лимит кандидатов (10/20/50) и стоимость запросов.
- Учитывать ли общественный транспорт (сейчас нет).
- Нужна ли пользователю возможность выбрать «справедливость vs скорость».
